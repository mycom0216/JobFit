# JobFit — 신입 개발 공고 선별·기술 적합도 분석 서비스

> 신입 개발자가 "아는 회사의 신입 공고"만 모아 보고, 공고가 요구하는 기술과 내 기술의 차이를 확인하는 백엔드 서비스

| | |
|---|---|
| 기간 | 2026.11 ~ (진행 중) |
| 형태 | 개인 프로젝트 |
| 기술 | Java 21, Spring Boot 4.1, Spring Data JPA, Spring Security + JWT, MySQL(운영)/H2(로컬), Redis 캐시, Gradle, JUnit 5 · Python FastAPI(RAG 검색) · 바닐라 JS 웹 화면 |
| 코드 | `JobFit/backend` · `JobFit/ai-service` · 문서 `JobFit/docs` |

## 1. 문제와 접근

- **문제**: 취업 포털 3곳에서 신입 개발 공고를 검색하면 헤드헌팅·파견·정체 불명 공고가 섞여 있고, 공고마다 요구 기술이 달라 비교가 어렵다.
- **접근**: 공고를 수집·분류(헤드헌팅/파견 제외, 유명기업 선별)하고, 본문에서 기술을 추출해 DB화한 뒤 검색·통계·적합도 API로 제공한다.
- **설계 근거**: 유명기업 신입 공고의 요구 기술(Java/Kotlin·Spring Boot·MySQL·Redis·Docker·CI, AI 직군은 RAG/LLM)을 직접 분석해 같은 스택으로 만들었다. (요구사항분석서 §2)

## 2. 데이터

1,475건 수집 → URL 중복 제거 1,097건 → 헤드헌팅/파견/교육생 38건 제외 → **1,059건 적재**(유명기업 99건, 그 외 960건, 기업 852곳). 분류 결과는 `채용공고_분석.xlsx`.

## 3. 직접 설계·구현한 부분

| 주제 | 내용 |
|---|---|
| 기술 추출 | 단순 포함 검색은 `Java`가 `JavaScript`에 걸린다. 기술별 경계 조건 정규식과 한글 별칭(스프링, 쿠버네티스)을 둔 사전을 만들고 단위 테스트로 고정 |
| N+1 방지 | 페이징 + 컬렉션 페치 조인은 메모리 페이징 경고가 난다. 페이지의 id만 먼저 뽑고 `EntityGraph`로 회사·기술을 한 번에 로딩 |
| 캐시 | 기술별 집계(전체 조인·그룹)는 무거워 `@Cacheable`. 프로필로 local=인메모리, prod=Redis(TTL 10분) 전환 |
| 인증 | BCrypt + 무상태 JWT. 로그인 실패 시 이메일 존재 여부를 노출하지 않는 동일 메시지, 위조·만료 토큰 401 |
| 멱등성 | 북마크 중복 요청을 DB 유니크 제약 + 사전 조회로 같은 결과 보장 |
| 장애 격리 | AI 서비스 호출에 연결 3초/응답 120초 제한, 실패 시 키워드 검색으로 대체(`fallback=true`) — AI가 꺼져도 API는 정상 |
| 적합도 | 공고 요구 기술 중 내가 가진 비율(0~100)과 일치/부족 기술을 함께 반환해 "무엇을 더 배울지"를 보여줌 |

## 4. 테스트

- 단위 4건: 기술 추출(Java/JavaScript 구분, 한글 별칭, 빈 입력), 점수 계산
- 통합 5건(실제 포트·HTTP): 유명기업 필터, 기술 필터·통계, 404/400, 가입→로그인→기술→매칭→북마크 전체 흐름(중복 가입 409, 잘못된 비밀번호 401, 토큰 없음/위조 401), AI 장애 대체
- 컨텍스트 로딩 1건 · **총 10건 통과** (`./gradlew test`)

## 5. AI 질문(RAG)과 웹 화면

- **검색**: BM25. 한글은 형태소 분석기 없이 2글자 단위 토큰 + 영문 단어 토큰. 제목·기업명에 가중치를 주려고 문서 앞부분을 중복 삽입.
- **답변**: 검색된 공고의 실제 필드(조건·요구 기술·비고)로 만든 정형 답변 + 근거 링크. 지어내는 문장이 없다.
- **시도했다가 접은 것**: ①임베딩 검색(embeddinggemma)은 개발 PC의 Ollama가 비정상 종료(0xc0000409)해 불가. ②로컬 3B 모델 생성 답변 2종을 시험했으나 둘 다 컨텍스트 첫 줄만 되풀이해 기본값에서 제외(`JOBFIT_USE_LLM=1` 옵션).
- **화면**: 공고 검색(필터·페이징), 기술 통계, AI 질문, 내 기술 선택 → 적합도 매칭(일치/부족 기술 표시), 관심 공고, 로그인/가입.
- 연동 확인: 웹 → Spring → FastAPI → 응답 0.01~0.03초(BM25, 1,059건 메모리 색인).

## 5-1. 한계 (정직하게)

- 의미 기반(임베딩) 검색은 미적용이라 "비슷한 뜻" 질의에는 약하다. 임베딩이 가능한 환경에서 교체하는 것이 다음 단계.
- 운영 프로필(MySQL+Redis)은 설정만 작성했고 이 환경에서 실행 검증하지 못했다. 캐시 성능 향상 수치는 **측정 전**이라 기재하지 않는다.
- 기술 추출은 상세 본문이 있는 19건 외에는 제목·직무 키워드 기반이라 불완전하다. "유명기업"은 주관적 목록이다.
- AI 서비스 Python 테스트 5건, 웹 화면은 수동 확인(자동 UI 테스트 없음).

## 6. 면접 예상 질문 대비

1. 왜 페이징에서 페치 조인을 안 썼나요? → 컬렉션 페치 조인은 `HHH90003004` 메모리 페이징을 유발. id 선조회 후 EntityGraph.
2. 캐시 무효화는? → 공고는 기동 시 적재만 되고 갱신 경로가 없어 TTL로 충분. 갱신 배치가 생기면 `@CacheEvict` 필요.
3. JWT 폐기는? → 현재 만료(120분)에만 의존. 로그아웃·탈취 대응은 블랙리스트/리프레시 토큰이 필요(미구현).
4. AI 장애 대체가 왜 필요한가요? → 외부 의존성 장애가 핵심 조회 기능으로 번지지 않게 격리.

## 7. 실행

```bash
cd JobFit/backend
./gradlew bootRun          # H2 + 인메모리 캐시, 화면: http://localhost:8080
./gradlew test             # 10건
cd ../ai-service && pip install -r requirements.txt
python -m uvicorn main:app --port 8000   # 없어도 백엔드는 대체 응답으로 동작
python -m pytest           # 5건
# 예) curl "http://localhost:8080/api/postings?famousOnly=true&size=5"
```
